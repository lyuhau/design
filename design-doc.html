Workflow Platform Design

Version 3. Covers the first release and what it must leave room for.

MVP: change request Next.js · Node · Postgres Kernel spec v2.7

1. Summary

We are rebuilding the Change Management intake as the first workflow on a small, generic workflow engine. The first release ships only that workflow, at parity with the existing product, with the workflow part made configurable.

  • The engine runs a small kernel: stages, transitions, waits and data writes. Everything an owner configures, such as an approval, expands into those parts.
  • Each request has an append-only history, kept forever, that is the source of truth. The engine records its decisions as events, so replaying a history never re-runs workflow logic.
  • Definitions are data, published through an API. A request stays on the version it started on.
  • Later workflows shaped the permanent parts (event shapes and IDs) but are not built. Five more use cases are recorded in the use cases doc.
This doc is the overview. The reference material lives in the workflow-platform folder: kernel-spec.md (the kernel, in full), expansion-battery.md (workflows expanded on paper to test the kernel), and test-cases/ (the change request as test data). Version 2.1 of this doc, with the earlier design and the detail for later use cases, is in this page's version history.

Scale is small: about one request every 10 seconds at most, across all future apps. Simplicity and correctness matter more than throughput.

Why build

The existing Change Management product is ours; this is its refactor. No product we reviewed covers the fixed needs without adding a JVM or a cluster to run: definitions as data published without a deployment, a permanent audit history as the source of truth, authorization checked when a person acts, and admin overrides recorded as skipped. Open-source BPMN engines (Operaton, Flowable) come closest and would still leave those four to build. Durable-execution engines (Temporal and similar) define workflows in code and do not keep history forever.

One engine hosts several apps. Each app is a namespace with its own pages and its own action-item list; apps share the engine and its tables, separated by a namespace column. There is no inbox shared across apps.

The UI is layered so later apps can reuse it: a headless client for the API, a set of UI components kept as a folder inside the app for now, and the Change Management pages on top.

4. The kernel

The kernel is the small set of parts the engine executes. The full rules are in kernel-spec.md.

PartWhat it isFirst release
StageA named scope. The root stage is always active, and exactly one child stage is active. Entering a stage opens its waits; leaving it cancels the ones still open. A final stage closes the request.Root plus one level
TransitionA condition and a target stage. The condition is checked against recorded state after every input; there are no trigger events. It can write data when it fires.Yes
WaitThe only thing that blocks. It opens, then closes once as completed, cancelled or skipped. A person wait is closed by an authorised person submitting an outcome and data. A call wait is closed by a connector's result.Person and call
SetA write to the request's data document, on a transition, at start, or by an admin.Yes
For eachOpens one person wait per item of a list fixed when the stage is entered.On person waits

How an input is processed

  1. One input (a start, a person acting, a call result, an admin action) is one turn, under a per-request lock, in one database transaction.
  2. The input is validated. A refused attempt writes nothing to history; it goes to a separate attempts log.
  3. decide reads the definition, evaluates conditions and writes events that spell out every consequence: which transition fired and what it read, which stage was entered, which waits opened with which resolved parameters.
  4. evolve folds events into state. Replay uses only evolve: it never evaluates a condition and never reads the definition.

The cost of recording decisions is that a bug in decide is recorded as fact. It is repaired by an admin turn, never by rewriting history.

Rules that shape everything else

  • No unsolicited input. Every inbound fact closes a wait the engine opened. There are no signals or correlation keys.
  • Joins are conditions. "All approved" or "any rejected" is an expression over the waits in the stage. An open wait always has a readable status, so these expressions are safe.
  • Results belong to one entry of a stage. Re-entering a stage gives fresh waits. Anything that must persist is written to data.
  • No clock. Each event carries its timestamp, and that is the only time the engine knows.
  • Errors never count as false. A failed condition rolls the turn back and marks the request faulted until an admin acts.
  • A stuck check runs after every turn. An open request with no open obligation and no open call is flagged for admins.

Events

Every event carries the request ID, a sequence number, a timestamp, the turn it belongs to, a schema version and the engine build. The vocabulary is provisional until a second workflow has been built on it.

KindEvents
Inputs from outsideRequestStarted, WaitCompleted, CallResultLate, Overridden
Decisions the engine recordedTransitionFired, StageEntered, StageExited, WaitOpened, WaitCancelled, WaitSkipped, DataSet, Faulted, RequestClosed, RequestReopened

A few fields exist only so later features need no change to old history: a stage entry records its parent entry, a wait ID carries a sequence number, and a request can record the request that started it. Each points to a case in the expansion battery.

5. The change request

A request has one primary domain and zero or more other domains, taken from the form. It only moves forward.

PendingOne approval per domain. The primary domain's approver picks the eng lead to approve. Each approval's directory call records who can approve.
all approve
In developmentThe eng lead marks the request released.
released
ReleasedFinal.

Any one rejection in Pending moves the request to Rejected (final) and cancels the approvals still open.

  • Submission never blocks. If a domain has nobody able to approve, the request still enters Pending and waits. A notification rule alerts the workflow admins from the recorded directory result.
  • Requesters cannot approve their own request. Group membership is checked when the person acts, and the lookup is recorded with the approval.
  • An admin can skip one domain's approval, but a skip never counts as an approval. To move the request on, the admin also jumps it forward and supplies the eng lead if nobody picked one.

Composites

The definition is written with two composites. Each is code in the repository, has a version, and expands into kernel parts when the definition is published. History never names a composite; the published definition records which composite, version and parameters each element came from. An expanded element's ID is the composite instance's ID plus a local name (primary.decision, primary.members, release.task), and it stays the same across composite versions when the element means the same thing. That is what lets a later migration find the approval an old event belongs to.

CompositeParametersExpands to
Approvalgroup; over (optional list, one approval per item); approveData; allowRequester (default false); outcome names (default approve and reject)A person wait marked as an obligation, the rule that the requester cannot act, the directory membership call, and the notification rule for "nobody is able to approve".
Taskassignee; outcomes (default done); doneDataOne person wait marked as an obligation.
  • An approval does not own a transition. It exposes two conditions, approved and rejected, and the workflow's own transitions decide what each one does. With over, approved means every item is approved and rejected means any item is rejected.
  • The change request uses two approvals and one task: the primary domain's approval (with the eng lead as its approval data), an approval over the other domains, and the eng lead's release task.
  • The new-task notification is a default rule on every definition, not a composite.

Example composite: domain approvals

A third composite is built as a worked example of how to write one. It is a fork of Approval for a primary group plus other groups, and it is the route to take when a workflow needs something Approval's parameters do not cover: fork it, do not add parameters. The change request does not use it in the first release.

  • Parameters: primaryGroup; otherGroups (a list); primaryApproveData; allowRequester (default false); outcome names.
  • Expands to: one directory call for all the groups (members), the primary's person wait (primary), one person wait per other group (others), and one "nobody is able to approve" rule (noApprover). Each ID is prefixed with the instance's ID.
  • Exposes the same approved and rejected conditions as Approval, and declares the same kind, approval, so pages and reports treat it as an approval.
  • What it shows a developer: derived element IDs, a version, the stored-expansion build test, a shared kind, and exposed conditions. Compared with two Approval instances it makes one directory call and sends one alert per request.

The definition and the happy-path events are in section 9 of the kernel spec. Ten cases (happy path, no other domains, no eligible approver, refused attempts, rejection, admin skip and jump, a jump during an in-flight call, an expression error) are written as test data in test-cases/c1-change-request.yaml.

To confirm Three assumptions about the existing product: approvals for all domains run in parallel; one rejection rejects the whole request; a person in two domains' groups may approve for both.

6. People and permissions

  • Who may act is decided when they act: the engine looks up the actor's group memberships, checks them against the wait's assignees and its rule, and records the lookup as evidence.
  • Who is being asked is recorded when the wait opens, as user and group references.
  • My action items are the open person waits marked as obligations whose assignees name me or a group I belong to now. Each app has its own list.
  • Viewing follows roles on the request: requester, approver, eng lead. Someone who used to hold a role keeps view access only.

Admin turns

An admin action is one recorded event followed by its consequences. An admin can skip one wait, jump to a stage, set data, disable a transition for one request, clear a fault, and close or reopen a request. Jumping into a stage requires the admin to supply, or explicitly waive, the data that stage needs. What was skipped is recorded as skipped, never as done.

Break-glass

The dev team holds standing super-admin access so a production problem never waits on a deployment or an entitlement request. A break-glass user can do anything an admin can, including on their own requests. Safeguards come from accountability (a required reason, a time-boxed session, a team alert, an after-the-fact review list), not from hard-coded limits. The first super-admins are seeded by a database migration.

7. Definitions and versions

  • A definition is a JSON document stored in the platform database and published through the API. There is no server CLI access, so the admin page that accepts JSON is the publishing tool.
  • A published version is immutable. A request stays on the version it started on, forever.
  • A saved draft of the intake form is not a request yet. It is checked against the latest version when submitted.
  • Conditions and computed values use CEL. Approver routing by domain is a CEL lookup, not a separate decision-table feature.
  • Publishing runs checks: expressions type-check, data is read only where it exists, every stage can reach a final stage, and every outcome leads somewhere. "Can never get stuck" cannot be proven in general; the runtime stuck check is the backstop.
  • The first release has two composites, Approval and Task, and one example composite, all written as code (section 5). Changing what a composite expands to requires a new composite version; a build test compares each expansion with a stored copy and fails otherwise.

The definition format and its CEL environment are a second long-lived contract: the engine must be able to run a version for as long as a request on it is open.

8. Integrations

SystemHow it connects
User directoryA call wait reads group members. The act-time membership check reads it too. The people picker for the eng lead searches it.
Email and SlackThe notifier consumes committed events and applies the definition's notification rules, delivering through the existing service. A sent notification is not part of a request's history.
Other systems, laterA call wait through a connector. A connector must honour the idempotency key and must never report "don't know" as a failure.

A call's result is recorded in history when it arrives, so replay never calls out. A result that arrives after its wait was cancelled is still recorded, as a late result that no condition can see.

Forms. The first release renders the intake form itself. Using the internal form creator app through its API remains the preferred long-term route and has not been evaluated.

All tables carry the namespace. History is kept forever; there are no snapshots, because replay is a cheap fold over a few dozen events.

10. Operations and cutover

  • Faults. A faulted request shows in an admin list with the element and error. It keeps recording inputs and resumes after an admin turn.
  • Stuck requests. Flagged automatically after any turn that leaves nothing open.
  • Calls. Delivered by a Postgres job queue that can enqueue inside the same transaction (Graphile Worker or pg-boss). A reconciler re-queues any open call with no delivery in flight.
  • Request inspector. An admin page showing a request's events, including which transition fired and the values it read.

Cutover

  • Requests already in flight finish in the existing product. New requests start in the new one.
  • Readable IDs in the new system start above the legacy maximum, so the two never collide.
  • Importing legacy requests is reconsidered after release. The request table reserves a legacy ID so it needs no schema change.

14. Open questions

  • Do the three approval assumptions in section 5 match the existing product?
  • Which directory API backs group membership and the people picker?
  • After what date are requests still open in the existing product imported or closed?
  • Does the existing product have saved drafts, SLA reminders or reports that must carry over? The parity checklist (M0) answers this.
  • Which JavaScript CEL library? It needs a short trial for conformance and custom functions.
  • Approvers editing a request's domain: the existing behaviour has known problems and is set aside for now.
  • Erasing personal data from a history that is kept forever: set aside for now.

15. Glossary

Request
One running instance of a workflow, such as a single change request.
Definition
The published description of a workflow: its stages, waits, transitions and notification rules.
Kernel
The small set of parts the engine executes: stage, transition, wait, Set.
Composite
Something an owner configures, such as an approval, that expands into kernel parts when published.
Stage
Where a request is. Shown to users as its status.
Activation
One entry of a stage. Re-entering a stage creates a new activation with fresh waits.
Wait
Something the request is waiting on: a person's action or a call's result.
Obligation / option
A person wait that someone is being asked to do, versus one they may do. Only obligations appear in action-item lists.
Transition
A condition that, when true, moves the request to another stage.
Turn
The processing of one input, in one database transaction.
History
The append-only list of a request's events. The source of truth.
Decide / evolve
decide works out what an input causes and records it as events. evolve applies events to state and is all that replay uses.
Replay
Rebuilding a request's state by applying its events in order.
Call
A request to an outside system through a connector, with a key that makes repeats safe.
Idempotency key
An identifier sent with a call so the outside system can recognise a repeat and not act twice.
Fault
A request the engine has flagged for an admin: an expression failed, or nothing is left open.
Admin turn
An admin's recorded intervention: skip, jump, set data, close or reopen.
Break-glass
Standing super-admin access for the dev team, for emergencies.
Namespace
One workflow app on the shared engine, with its own pages and lists.
CEL
Common Expression Language, used for conditions and computed values.
Expansion battery
Workflows expanded on paper into kernel parts and events, to test that the kernel can express them.
Insurance field
A field recorded now only so a later feature needs no change to old history.
Drain
Letting in-flight requests finish in the old system while new ones start in the new one.
